# ТЗ на React-прототип «Назначение бригады на заявку»

## 1. Цель

Разработать кликабельный frontend-прототип одного экрана внутренней системы компании «Каналсервис» — **«Заявки на выезд»**.

Прототип должен демонстрировать полуавтоматический процесс назначения бригады:

**заявка → автоматический подбор бригады → подтверждение диспетчером → назначение**

и обязательные нештатные сценарии:

- конфликт параллельного назначения;
- недостаточно прав;
- отсутствие подходящей бригады.

Это **демонстрационный прототип для тестового задания**, а не production-система.

---

## 2. Технологические требования

Использовать:

- React;
- желательно TypeScript;
- Vite;
- обычный CSS / CSS Modules;
- можно использовать Lucide Icons;
- без backend;
- без базы данных;
- без внешних API;
- без авторизации;
- все данные mock;
- все изменения состояния хранятся только в React state.

Приложение должно запускаться командами:

```bash
npm install
npm run dev
```

И успешно собираться:

```bash
npm run build
```

Не использовать тяжёлые UI-фреймворки без необходимости.

---

## 3. Главное ограничение

Прототип должен представлять **один основной экран**.

Не создавать:

- отдельный кабинет руководителя;
- отдельный кабинет бригадира;
- отдельную страницу входа;
- полноценную CRM;
- настройки;
- аналитику;
- карту;
- большой набор страниц.

Допустимы:

- modal;
- drawer;
- dropdown;
- toast;
- confirmation dialog.

Они считаются состояниями того же экрана.

Статусы должны легко читаться.

Например:

- **Плановая** — нейтральный badge;
- **Требует назначения** — жёлтый/оранжевый;
- **Назначена** — зелёный;
- **Конфликт** — красный.

Это внутренний рабочий интерфейс.

Стиль:

- desktop business application;
- спокойный;
- функциональный;
- много информации;
- минимальная декоративность.

## 10. Подтверждение автоматического выбора

После автоматического выбора показать кнопки:

```text
[ Назначить бригаду №3 ]

[ Выбрать другую ]
```

При назначении:

1. статус заявки меняется:

```text
Требует назначения
→
Назначена
```

2. появляется:

```text
Бригада №3
```

3. показать toast:

> Бригада №3 назначена на заявку №10427

4. состояние должно измениться и в таблице.

---

## 11. Ручное изменение рекомендации

Если диспетчер нажимает:

> Выбрать другую

показать список доступных бригад.

После выбора другой бригады обязательно показать поле:

> Причина изменения рекомендации

Textarea обязательный.

Placeholder:

```text
Укажите причину выбора другой бригады
```

Примеры причины:

- ограничение по адресу;
- договорённость с заказчиком;
- бригада фактически недоступна;
- другое.

Кнопка:

> Назначить

должна быть disabled, пока комментарий пустой.

После назначения сохранить комментарий только в React state.

## 12. Сценарий №1 — обычная работа

Прототип обязательно должен позволять пройти следующий путь:

```text
1. Открыть заявку №10427
2. Нажать «Выбрать автоматически»
3. Получить рекомендацию «Бригада №3»
4. Нажать «Назначить бригаду №3»
5. Получить успешное назначение
```

Финальный вид:

```text
Статус: Назначена
Бригада: №3
```

---

## 13. Сценарий №2 — конфликт параллельного назначения

Это один из ключевых сценариев прототипа.

Добавить способ его воспроизвести.

Лучший вариант — отдельная небольшая кнопка:

> Симулировать конфликт

Она может находиться в меню:

```text
⋮ Демонстрация сценариев
```

или в нижней части drawer.

После включения conflict mode пользователь:

1. открывает заявку №10428;
2. получает рекомендацию;
3. нажимает «Назначить».

В этот момент система должна имитировать ситуацию:

> Другой диспетчер уже назначил эту заявку на Бригаду №5.

Показать modal.

### Заголовок

> Назначение изменилось

Текст:

> Пока вы работали с заявкой, другой диспетчер назначил на неё Бригаду №5.

Дополнительная строка:

```text
Изменено:
Марина Петрова
14:41
```

Кнопка:

> Обновить данные

После нажатия:

```text
Текущее назначение:
Бригада №5
```

Статус:

> Назначена

Важно:

**не создавать второго назначения.**

---

## 14. Смысл конфликтного сценария

Прототип должен явно показывать бизнес-правило:

> Одна заявка не может одновременно иметь две активные бригады.

Если состояние изменилось после открытия заявки, пользователь должен увидеть актуальные данные, а его устаревшая команда не должна выполниться.

## 15. Сценарий №3 — недостаточно прав

В selector роли выбрать:

> Бригадир

Затем открыть заявку.

Бригадир должен видеть заявку, но:

- кнопка «Выбрать автоматически» недоступна;

или при клике показывается modal.

Лучше второй вариант, поскольку он лучше демонстрирует требуемое состояние.

Modal:

### Недостаточно прав

```text
У вашей роли нет права назначать и переназначать бригады.

Для выполнения операции обратитесь к диспетчеру или руководителю.
```

Кнопка:

> Понятно

Назначение при этом не изменяется.

---

## 16. Права ролей

Использовать следующую модель.

### Диспетчер

Может:

- смотреть заявки;
- запускать автоматический подбор;
- назначать бригаду;
- выбирать другую бригаду;
- переназначать.

### Руководитель

То же, что диспетчер.

Можно дополнительно показать строку:

> История назначения

но отдельный экран не создавать.

### Бригадир

Может:

- смотреть заявку;
- видеть назначенную бригаду.

Не может:

- выбирать бригаду;
- менять назначение;
- запускать автоматический подбор.

## 17. Дополнительный error-state

Кроме обязательного конфликта желательно реализовать:

> Нет подходящих бригад

Например, для заявки:

```text

Тип работ: Телеинспекция
```

> Выбрать автоматически

```text

```

Кнопки:

```text
[ Обновить ]

[ Оставить на ручном назначении ]
```

Это полезно для демонстрации принципа:

> система не обязана принимать решение любой ценой.

## 19. Бизнес-правила prototype

Реализовать в mock-логике следующие правила.

### BR-01

На заявку может существовать только одно активное назначение.

### BR-02

На занятую бригаду новую заявку назначить нельзя.

### BR-03

Автоматический подбор рассматривает только свободные бригады.

### BR-04

Для телеинспекции подходят только бригады с соответствующим оборудованием.

### BR-05

Если подходящей бригады нет:

автоматическое назначение не производится.

### BR-06

Диспетчер может изменить рекомендацию системы.

### BR-07

При изменении рекомендации требуется комментарий.

### BR-08

Бригадир не может выполнять назначение.

### BR-09

Если заявка изменилась после того, как была открыта пользователем:

устаревшее назначение не выполняется.

Показать конфликт.

## 20. История действий

В нижней части drawer сделать компактный блок:

> История

Например:

```text
14:32  Заявка создана
14:35  Автоматически предложена Бригада №3
14:36  Игорь Смирнов назначил Бригаду №3
```

Для ручного изменения:

```text
14:37
Игорь Смирнов выбрал Бригаду №7 вместо рекомендованной №3

Причина:
Бригада №3 сообщила о задержке на предыдущем объекте
```

Для прототипа достаточно хранить историю в state.


## 36. Требования к качеству кода

Код должен быть:

- простой;
- читаемый;
- без overengineering;
- без ненужных abstractions;
- компоненты не должны быть чрезмерно крупными;
- TypeScript без `any`, где это разумно;
- консоль браузера без ошибок;
- никаких TODO в финальной версии;
- никаких незавершённых placeholder-компонентов.
