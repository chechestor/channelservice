# Patch Backlog

Skill для бизнес- и системного аналитика: ведение заданий на доработку в `.tasks/patches.md`.

## Когда применять

- Пользователь надиктовал правки / пожелания / «хочу чтобы…»
- Нужно оформить или обновить задание на доработку
- Просят посмотреть / приоритизировать / закрыть патчи
- Упоминают `patches.md`, P001, доработки, бэклог правок

## Файл

Путь: **`.tasks/patches.md`**

Если файла нет — создай по шаблону из этого skill.

## Workflow

1. **Разобрать ввод**
   - Выделить одну или несколько независимых доработок
   - Для каждой: цель, что меняется, что не меняется, критерий «готово»

2. **Назначить номер**
   - Прочитай текущий `.tasks/patches.md`
   - Следующий номер = max(Pxxx) + 1, формат `P001`, `P002`, …
   - Не перенумеровывай старые патчи без явной просьбы

3. **Обновить перечень в начале файла**
   - Добавь строку: `- [ ] P0NN — Краткое название`
   - При выполнении: отметь `[x]`
   - Порядок в перечне: обычно по номеру (P001 → …); срочные можно пометить `(срочно)` в названии

4. **Добавить подробную секцию**

Используй шаблон ниже. Не оставляй пустых обязательных полей — если неизвестно, пиши «Допущение: …» или «Уточнить у заказчика: …».

5. **Отчитаться**
   - Список новых/изменённых P0NN одной короткой сводкой

## Шаблон подробной секции

```markdown
## P0NN — Краткое название

| Поле | Значение |
|------|----------|
| Статус | open \| in_progress \| done \| cancelled |
| Источник | надиктовка / ссылка на сообщение |
| Связь | спека / экран / компонент (если есть) |

### Цель

Зачем эта доработка (1–3 предложения).

### Что сделать

- Конкретные изменения UI / поведения / данных
- …

### Что не делать

- Ограничения и out of scope

### Критерии приёмки

- [ ] …
- [ ] …

### Заметки

Допущения, риски, открытые вопросы.
```

## Правила качества

- Название в перечне = название в заголовке секции
- Описание исполнимое: без «улучшить UX» без конкретики
- Один патч не смешивает несвязанные темы
- Не удаляй историю done/cancelled без просьбы — лучше отмечай статус
- Код и файлы приложения не трогай в рамках этого skill

## Анти-паттерны

- Править только перечень без детальной секции (или наоборот)
- Пропускать номера (P001, P003 без P002) без причины в заметках
- Писать реализационные детали уровня «использовать useEffect» — только если это требование заказчика
