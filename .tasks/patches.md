## P001 — Режим доски (канбан) как основной + список с фильтрами

| Поле | Значение |
|------|----------|
| Статус | done |
| Источник | надиктовка 11.09.2026, п. 1 |
| Связь | `tasks/specs/назначение-бригады/`; экран «Заявки на выезд»; `Header`, `RequestsTable`, `FilterChips`, `App` |

### Цель

Первый прототип показывает заявки только плоским списком/таблицей — этого недостаточно. Нужен основной режим **доски** (канбан по статусам) и сохранение **списка** как второго режима с полноценным поиском и фильтрами.

### Что сделать

- В шапке экрана (рядом с заголовком «Заявки на выезд» или в `Header`) добавить переключатель режимов: **Доска** / **Список**.
- Режим **Доска** — основной: открывается по умолчанию при заходе на экран.
- Доска: колонки = статусы заявок. Карточки-тикеты лежат в колонке своего статуса и **переезжают**, когда статус меняется.
- На доске **не показывать** заявки в статусах **Отменена** и **Завершена** (колонок для них нет).
- Карточка на доске: достаточно для опознания (номер, тип, адрес, SLA/срочность, исполнитель и/или бригада — что уже есть в модели). Клик открывает текущий drawer заявки (с учётом P002).
- Режим **Список**: полный перечень заявок, включая завершённые и отменённые.
- В списке — фильтры и поиск:
  - период по дате создания (от / до);
  - поиск по адресу;
  - прочие параметры заявки: тип, статус, вид работ, источник (минимум — текстовый поиск + фильтр по типу и статусу).
- Текущие chips «Все / Аварийные / Требуют назначения / Назначенные» оставить в режиме списка либо заменить эквивалентными фильтрами; на доске chips не обязательны (колонки уже режут по статусу).
- Mock-данные: расширить статусы и добавить 1–2 завершённые и 1 отменённую заявку, чтобы список отличался от доски.

**Допущение по статусам доски** (сейчас в коде только `unassigned` / `assigned` / `completed`):

| Статус (UI) | На доске | Примечание |
|-------------|----------|------------|
| Новая | да | входящая, ещё никто не взял (P002) |
| В работе | да | диспетчер взял заявку, бригада ещё не назначена |
| Назначена | да | назначена бригада |
| Завершена | нет | только список |
| Отменена | нет | только список; статус сейчас отсутствует — добавить |

Текущий `unassigned` («Требует назначения») на доске разложить на **Новая** и **В работе**. Назначение бригады по-прежнему переводит в **Назначена**.

**Допущение по перемещению:** карточка меняет колонку при смене статуса (взятие в работу, назначение бригады). Drag-and-drop между колонками доски — желателен в прототипе; если трудоёмко в этом шаге, допустим без DnD, но тогда явно оставить карточки кликабельными и движущимися после действий в drawer. Broсить в «Завершена»/«Отменена» с доски нельзя (колонок нет).

### Что не делать

- Не убирать режим списка — он остаётся вторым режимом.
- Не делать отдельные страницы/роуты на каждый режим, если достаточно состояния на одном экране.
- Не строить полноценный Jira/Trello (WIP-лимиты, swimlanes, архив колонок).
- Не менять сценарии назначения бригады, конфликта и прав (BR-01…BR-09), кроме отображения результата на доске.
- Не подключать бэкенд.

### Критерии приёмки

- [ ] При открытии экрана по умолчанию видна **доска**, не таблица.
- [ ] В шапке есть переключатель «Доска» / «Список»; выбор сразу меняет отображение заявок.
- [ ] На доске есть колонки действующих статусов; **Отменена** и **Завершена** отсутствуют как колонки и как карточки.
- [ ] Карточка заявки находится в колонке своего статуса; после смены статуса (в т.ч. через P002 и назначение бригады) карточка оказывается в другой колонке без перезагрузки страницы.
- [ ] Клик по карточке открывает существующую карточку/drawer заявки.
- [ ] В режиме «Список» видны все заявки, включая завершённые и отменённые.
- [ ] В списке работают фильтр по датам, поиск по адресу и фильтры/поиск по прочим полям заявки; пустой результат поиска показывает понятное пустое состояние.
- [ ] Переключение Доска ↔ Список не сбрасывает demo-сценарий (и сессию диспетчера, см. P003).

### Заметки

- Визуал доски: тот же внутренний business UI, что и у прототипа (не маркетинговый канбан).
- Состояние переключателя достаточно держать в React state (без URL), пока нет требования шарить ссылку на режим.
- P002 зависит от статуса **Новая** и поля исполнителя — реализовывать лучше вместе или сразу после расширения статусов в P001.
- Уточнить у заказчика: нужен ли drag-and-drop в первом заходе или достаточно «карточки едут сами после действий».

## P002 — Взятие новой заявки в работу (модалка Да/Нет + исполнитель)

| Поле | Значение |
|------|----------|
| Статус | done |
| Источник | надиктовка 11.09.2026, п. 2 |
| Связь | `tasks/specs/назначение-бригады/`; drawer заявки; роли в `src/data/users.ts`; зависит от статусов P001 |

### Цель

Новую заявку нельзя «просто открыть и работать»: диспетчер явно подтверждает, что берёт её на себя. После согласия он становится **исполнителем** заявки.

### Что сделать

- При открытии заявки в статусе **Новая** (клик по строке списка или карточке доски) **сначала** показать модальное окно:
  - текст: «Хотите взять эту заявку в работу?»
  - кнопки: **Да** / **Нет**.
- **Да:**
  - в заявку записывается поле **Исполнитель** = текущий диспетчер (ФИО: Игорь Смирнов);
  - статус заявки: **Новая → В работе**;
  - запись в истории заявки (например: «Игорь Смирнов взял заявку в работу»);
  - после этого открывается обычный drawer заявки; исполнитель виден в деталях.
- **Нет:**
  - исполнитель не заполняется, статус не меняется;
  - модалка закрывается, drawer **не** открывается.
- Модалку показывать только для статуса **Новая**. Прототип всегда от лица диспетчера (см. P003).
- Повторное открытие заявки уже **В работе** / **Назначена** / др. — без этой модалки, сразу drawer.
- Если у заявки уже есть исполнитель, модалку не показывать.

**Допущение:** «исполнитель заявки» — диспетчер, взявший тикет, **не** бригада. Назначение бригады остаётся отдельным шагом в drawer.

### Что не делать

- Не подменять этой модалкой сценарии назначения бригады, конфликта и «недостаточно прав».
- Не спрашивать «взять в работу» при каждом повторном открытии той же заявки.
- Не реализовывать передачу заявки другому диспетчеру, очередь и эскалацию — вне scope.
- Сценарии «руководитель» и «бригадир» сняты патчем P003 — не закладывать ветки по ролям.

### Критерии приёмки

- [ ] Открытие заявки со статусом **Новая** (с доски и из списка) показывает модалку «Хотите взять эту заявку в работу?» с кнопками Да и Нет.
- [ ] Да: исполнитель = диспетчер Игорь Смирнов, статус «В работе», поле исполнителя видно в карточке, заявка на доске переезжает из «Новая» в «В работе».
- [ ] Нет: статус и исполнитель без изменений, карточка заявки не открывается.
- [ ] Повторный вход в ту же заявку после «Да» — без модалки.
- [ ] Назначение бригады по-прежнему доступно после взятия в работу (существующий happy-path).

### Заметки

- Если P001 ещё не расширил статусы: минимально ввести **Новая** и **В работе** и поле `executor` (диспетчер) на заявке.
- Вопрос про руководителя снят: P003 фиксирует единственную роль — диспетчер.
- Риск: два человека в разных вкладках — в прототипе без бэкенда конфликт взятия в работу не моделируем, пока не попросят (конфликт уже есть только для назначения бригады).
- **Снято P007:** кнопка **Нет** (закрыть без открытия карточки) заменена на **«Только открыть»**. Критерий «Нет → карточка не открывается» больше не действует.

## P003 — Убрать выбор роли: только диспетчер

| Поле | Значение |
|------|----------|
| Статус | done |
| Источник | надиктовка 11.09.2026, п. 3 |
| Связь | `Header`, `RoleSelector`; `tasks/specs/назначение-бригады/` (селектор ролей, сценарий «недостаточно прав»); уточняет P001 и P002 |

### Цель

Прототип больше не демонстрирует разные роли. Интерфейс и поведение — только для **диспетчера**. Выбор роли в шапке мешает и должен исчезнуть.

### Что сделать

- Убрать из UI переключатель / выпадающий список ролей (`RoleSelector`: Диспетчер / Руководитель / Бригадир).
- Сессия всегда: роль **Диспетчер**, пользователь **Игорь Смирнов** (текущий mock).
- В **правом верхнем углу** шапки обязательно оставить блок текущего пользователя (не кликабельный, роль не меняется):
  - подпись: **«Диспетчер Игорь»**;
  - рядом — **аватар**: круглый кружок с мультяшным лицом (иллюстрация/иконка, не фото и не инициалы).
- Аватар декоративный: без меню, без загрузки файла, без смены картинки.
- Назначение бригады, взятие заявки в работу (P002), доска и список (P001) работают сразу, без смены роли.
- Сценарий «недостаточно прав» через роль «Бригадир» больше не воспроизводится: убрать вход в `PermissionModal` из рабочего потока и пункт demo, если он завязан на смену роли.
- Demo-меню оставить для сброса, конфликта назначения и «нет свободных бригад».
- Ветки UI «только просмотр для бригадира» и «история для руководителя» не поддерживать.

### Что не делать

- Не делать логин, SSO и выбор пользователя.
- Не заменять аватар инициалами, серым плейсхолдером или фотореалистичным портретом — нужно именно круглое мультяшное лицо.
- Не оставлять скрытый переключатель «для демо» (URL, query, горячие клавиши).
- Не переписывать исходное ТЗ в `tasks/specs/` в этом патче: для реализации приоритет у `patches.md`; расхождение со спекой (три роли, BR-08 в UI) — ожидаемое.
- Не трогать назначение бригады и конфликт параллельного назначения.

### Критерии приёмки

- [ ] На экране нет контрола выбора роли.
- [ ] Нельзя переключиться на руководителя или бригадира.
- [ ] Пользователь всегда диспетчер; назначение бригады доступно без дополнительных жестов.
- [ ] Модалка «Недостаточно прав» не открывается в штатном сценарии (нет роли без прав).
- [ ] P002: исполнитель при «Да» — всегда Игорь Смирнов; отдельных правил для бригадира нет.
- [ ] В правом верхнем углу шапки видно **«Диспетчер Игорь»** и круглую аватарку с мультяшным лицом.
- [ ] Клик по имени или аватару не открывает выбор роли и не меняет пользователя.

### Заметки

- Исходное ТЗ держало три роли ради демо BR-08. Заказчик это отменяет для текущего прототипа.
- Типы `Role` / профили manager и crew_leader в коде можно упростить или оставить мёртвыми — на усмотрение разработчика, в UI их быть не должно.
- При реализации P001/P002 опираться на эту роль, а не на старые критерии P002 про бригадира (они сняты).
- Уточнение заказчика (после первой реализации): имя и аватар в правом верхнем углу обязательны, не опциональны. Патч снова **open**, пока это не принято.

## P004 — Создание заявки с кнопки [+] и поиск совпадений по адресу

| Поле | Значение |
|------|----------|
| Статус | done |
| Источник | надиктовка 11.09.2026, п. 4 |
| Связь | колонка «Новая» (P001); модалка взятия в работу (P002); сущность `Request` |

### Цель

Диспетчер должен сам заводить заявки с доски, а не только разбирать готовый список. Перед дублем по адресу система показывает уже активные заявки на тот же объект, чтобы можно было уйти в существующую вместо новой.

### Что сделать

- В заголовке колонки **Новая** справа от названия — кнопка **[+]** (создать заявку).
- По [+] открывается **модальное окно создания заявки**.
- Первое поле формы — **Адрес** (всегда сверху, в фокусе при открытии).
- Остальные поля формы (минимум для прототипа): тип (аварийная / плановая), вид работ, источник. Кнопки: **Создать** и **Отмена**.
- После успешного создания заявка появляется в колонке **Новая** (без исполнителя). Дальше действует P002: при открытии карточки — «взять в работу?».

**Поиск совпадений по адресу**

- По мере ввода адреса система ищет среди **активных** заявок (статусы **Новая**, **В работе**, **Назначена**; не Завершена и не Отменена).
- Совпадение: подстрока в адресе, без учёта регистра (например «ленина» находит «Ленина, 14»).
- Список совпадений — **отдельный блок рядом с полем адреса** (не выпадашка внутри инпута и не вместо формы). Пока адрес пустой или слишком короткий — список пустой/скрыт; при отсутствии совпадений — короткое «Совпадений нет».
- В строке совпадения: номер, адрес, статус, тип — чтобы отличить заявки.

**Просмотр найденной заявки**

- Клик по строке совпадения открывает **второе модальное окно** — просмотр этой активной заявки (номер, адрес, тип, статус, работы, исполнитель/бригада). Это не замена drawer назначения.
- Во втором окне кнопка **«Продолжить здесь»**:
  - создание новой заявки **отменяется** (форма закрывается, черновик не сохраняется);
  - диспетчер переходит к выбранной существующей заявке (открывается её обычный drawer; если статус **Новая** — срабатывает P002).
- Закрытие второго окна (крестик / Отмена / клик вне, если так принято в прототипе) **не** отменяет создание: форма новой заявки остаётся открытой, ввод сохраняется, можно продолжить создавать.

**Mock:** в данных должна быть хотя бы одна пара активных заявок с пересекающимся адресом, чтобы совпадения было чем показать.

### Что не делать

- Не добавлять [+] в колонки «В работе» и «Назначена».
- Не искать среди завершённых и отменённых.
- Не подключать геокодер, ФИАС, карту.
- Не делать жёсткую блокировку создания при совпадении: диспетчер может закрыть просмотр и всё равно создать новую заявку на тот же адрес.
- **Уточнение P010:** перед созданием при видимых совпадениях — запрос подтверждения (Да/Нет), не запрет.
- Не запускать назначение бригады из окна создания.

### Критерии приёмки

- [ ] У заголовка колонки «Новая» есть кнопка [+]; по нажатию открывается модалка создания, адрес — первая строка.
- [ ] Ввод адреса показывает отдельный список активных заявок с похожим адресом рядом с формой.
- [ ] Завершённые и отменённые в совпадениях не появляются.
- [ ] Клик по совпадению открывает второе окно просмотра; форма создания при этом не закрывается.
- [ ] «Продолжить здесь»: модалка создания закрывается без новой заявки, открывается выбранная существующая (с P002, если она Новая).
- [ ] Закрытие окна просмотра без «Продолжить здесь» возвращает к форме создания с сохранённым вводом.
- [ ] «Создать» добавляет заявку в колонку «Новая»; «Отмена» на форме ничего не создаёт.

### Заметки

- Допущение: кнопка [+] только на доске, в режиме списка отдельной кнопки создания нет (пока не попросили).
- Допущение: поиск с 2 символов, чтобы не шуметь на одной букве.
- Стек модалок: создание снизу, просмотр сверху. Не подменять просмотр полным drawer, пока не нажато «Продолжить здесь».
- Дополнение: многострочное **описание** заявки — см. P008.
